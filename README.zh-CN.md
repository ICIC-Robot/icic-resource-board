# ICIC 资源看板

[English](README.md) | 中文

[打开实时看板](https://icic-robot.github.io/icic-resource-board/)

ICIC 资源看板公开、只读地展示 UF HiPerGator 上 `du.j` 组的共享配额、Slurm 队列以及 `/blue/du.j` 存储用量。组内成员可以用它查看当前需求、理解共享 QOS 余量，并判断下一个作业适合申请多少资源、何时提交。

本看板并非 UF 官方服务，也不能替代 Slurm 这一权威数据源。

## 只读边界

看板不能提交、取消、重新排队、调整优先级或修改任何 HiPerGator 作业，也不能更改账户、QOS 限额、分区、预约或资源配额。采集器只读取调度器信息，再生成字段范围受限的公开快照。启动时间估计来自 `sbatch --test-only`：Slurm 只计算假设的开始时间，不会提交任何作业。

公开快照包含用户名、作业名称和 ID、资源请求、作业状态、调度时间窗口及每位成员的存储总量；其他组的排队需求只按分区汇总成数字（GPU 数、核心数、作业数），不含任何用户或作业信息；不包含节点名、执行命令、工作目录、环境变量、凭据及未识别的 Slurm 字段。网页不会收集 UF 密码、SSH 密钥或登录会话。

## 运行方式

1. HiPerGator 的 Slurm `scrontab` 每 5 分钟触发一次 `duj-github-snapshot`。
2. 每次运行申请 1 个 CPU、512 MiB（0.5 GiB）内存，不申请 GPU，在 `hpg-dev` 中最长运行 2 分钟。
3. 采集器读取 `du.j` 的 Slurm 队列、`du.j` 与 `du.j-b`（burst）两个 QOS、7 天 `sacct` 记录、各分区 `sinfo` 空闲情况与排队需求、几个标准请求的 `sbatch --test-only` 估计，以及 `/blue/du.j` 配额（共约 5–7 秒），生成公开的 `status.json` 快照（约 20 KB）。
4. 仅限本仓库的 GitHub Deploy Key 将快照推送到 `data` 分支。
5. GitHub Pages 从 `main` 分支发布看板。浏览器每 60 秒用带 ETag 的条件请求检查一次快照：快照没变时 GitHub 返回 304，不计入未认证 API 每 IP 每小时 60 次的限额；切回标签页时也会立即检查。最近一次成功读取的数据缓存在浏览器中。

发布任务本身是普通 Slurm 作业，因此会短暂出现在队列里。它不会常驻运行，也不会占用 GPU。

### 存储数据采集

Lustre 只允许每个用户查看自己的配额，因此成员存储用量有两种来源：

| 来源 | 方式 | 显示为 |
| --- | --- | --- |
| 组总量 | 每 5 分钟对 `/blue/du.j` 项目执行 `lfs quota -p` | 精确 |
| 发布器所有者 | 发布器以 jinjiaguo 身份运行，每 5 分钟直接读取该账户的 `lfs quota -u` | **精确** |
| 成员自报（自愿） | 成员自己的 scrontab 每 3 小时运行 `report_storage.sh` 的私有副本（位于 `~/.local/bin`），将本人的 `lfs quota -u` 总量写入 `storage-reports/<uid>.json` | **精确** |
| 每日扫描（兜底） | `scan_storage.py` 每天 04:30 对每位成员的顶层目录运行 `du`（`hpg-default`，4 CPU，2 GiB，≤ 3 小时） | **扫描**；部分子目录组内不可读时为 **≥ 部分扫描**；整个目录不可读时为 **目录不可读** |

未能归属到成员的部分显示为 **未归属**（组总量 − 已统计成员），主要来自不可读目录。只公开总量和文件数，不公开路径。只有文件所有者与报告中的用户一致时，发布器才接受自报数据。

想分享自己的精确用量，在 HiPerGator 上运行一次（用 `--uninstall` 停止）：

```bash
/blue/du.j/jinjiaguo/duj-github-snapshot/report_storage.sh --install
```

采集器源码保存在 [`collector/`](collector/)，部署于 `/blue/du.j/jinjiaguo/duj-github-snapshot/`。

## 各板块含义

侧边栏按"当前 / 集群 / 组内 / 说明"分组，点击跳转到对应板块；手机上从左上角菜单打开。

### 数据时间

顶栏显示快照的生成时间（美东时间）、距今多久，以及下一次发布的大致时间（每 5 分钟一次）。侧边栏底部的标记表示数据来源：**实时快照**、**浏览器缓存**（实时接口暂时不可用）或**预览数据**（演示内容）。快照超过 15 分钟未更新会显示延迟提示，此时请直接在 HiPerGator 上确认。

### 现在能用多少

每种 GPU 一张卡片，外加 CPU 任务一张：

- **可立即启动** = 组 QOS 剩余额度，与"分区空闲 − 排在我们前面的排队请求"两者中较小的一个。
- **排在我们前面**：该分区上因 `Resources`/`Priority` 在排队、且优先级不低于本组新任务的请求总量（按分区汇总，来自所有用户）。物理空闲的卡如果已经有优先级更高的请求在等，就不算可用。本组新任务的优先级取组内当前主 QOS 作业中最低的那个作为近似。
- **单节点最多**：一个任务最多能拿到的 GPU 数（受限于单个节点的空闲卡数）。

### 组额度

`du.j`（主额度）与 `du.j-b`（burst）分开显示，每项给出在用、空闲、上限，进度条按成员着色。排队中的任务在启动前不占任何额度。

- **du.j**：正常优先级；GPU 任务只能用这个 QOS。
- **du.j-b（burst）**：纯 CPU（0 张 GPU），单任务最长 4 天，优先级低得多，只用集群富余的资源；它的用量不占 du.j 额度。

看板自己的采集任务（`duj-github-snapshot` 等）单独标为"看板采集"，不计入任何成员。

### 排队

排队任务按等待原因分为四组，只有第一组会和新请求竞争资源：

- **等待资源**：在等节点或额度（`Resources`、`Priority`、`QOSGrp*` 等），以及限速数组当前空出的槽位。
- **数组限速**：在等自己数组 `%N` 并发上限（`JobArrayTaskLimit`）。这些任务只有在同一数组有任务结束时才会启动，不额外占用组额度。例如 `--array=0-413%8` 的数组，任何时候最多 8 个在跑，其余几百个任务只是在排自己的队。下方列出每个数组的剩余任务数和并发情况。
- **依赖 / 暂停 / 个人上限**：在等其他任务、被暂停或超过个人上限。
- **预约**：设定稍后开始的任务（`--begin`、scrontab）。

### 分区空闲

来自 `sinfo`：各分区全体用户共享的物理空闲 GPU（`hpg-default` 为空闲核心）、单节点最多空闲数和可用节点数，以及其他用户在该分区排队的 GPU 总量（其中多少优先于本组）。宕机、排空或维护中的节点不计入。

### 多久能排到

针对几种标准请求（1 张 B200 / RTX PRO 6000 / L4，8 核 CPU，以及 burst，均为 4 小时）给出判断：

1. 组额度有余、某个节点有足够空闲、且没有更高优先级的请求在等这些资源时，显示**现在**。
2. 组额度已满时，按运行中任务用满时限推算**最晚**何时空出槽位；它们提前结束会更早。
3. 分区被更高优先级的请求占满时，以 Slurm 的估计为准，显示**约**某个时间。

Slurm 的估计（`sbatch --test-only`）假设所有任务都用满时限，是会变动的保守上界；能立即启动时不再显示它。

### 检查我的请求

输入分区、GPU 数、CPU、内存和时长后，依次检查：QOS 上限与运行时限、组内当前余量（已满时估算何时释放）、组内正在等资源的需求、分区是否有单个节点能容纳、是否有更高优先级的请求在排队；纯 CPU 任务还会提示是否可以改用 burst。输入保存在浏览器中。下方图表是未来 24 小时组内 GPU 占用（假设运行中任务用满时限）。

### 成员与任务

成员表显示每人的运行数、等资源数、数组排队数、GPU（按型号）、CPU、内存、burst CPU 和存储用量；点击成员可筛选任务列表。

任务表按"运行中 / 等资源 / 数组限速 / 预约·其他"分类，相同请求合并为一行并显示 `×N`。运行中任务显示"最晚 X 结束"（开始时间 + 时限，通常会更早结束）；排队任务显示 Slurm 的启动估计；数组限速任务显示"随数组空出槽位依次启动"。

### 最近 7 天、存储

与之前相同：来自 `sacct` 的每小时使用量、按成员的每日 GPU/CPU·小时与失败率；`/blue/du.j` 按成员拆分的用量、来源标签和增长趋势。

### 链接与分享

筛选状态保存在网址中，例如 `?member=xianyao.li&filter=waiting&lang=zh` 会打开相同视图（`filter` 可选 `running`、`waiting`、`throttled`、`other`）。

## 如何据此安排作业

1. 确认顶栏数据时间是最近几分钟。
2. 看"现在能用多少"：目标 GPU 型号的可立即启动数是否 ≥ 你的单任务需求，并留意"单节点最多"。
3. 不够时看"多久能排到"：是组额度满（等组内任务结束），还是分区被更高优先级的请求占满（参考 Slurm 估计，或换一种 GPU）。
4. 纯 CPU、不超过 4 天的任务可以考虑 burst（`--qos=du.j-b`），不占组额度。
5. 大批量任务用 `--array=...%N` 限制并发，给组内其他人留出额度；看板会把数组排队与真正的资源竞争分开显示。

提交后在**任务**中找到自己的作业，它的状态和原因比汇总数字更能说明问题。需要权威结果时，请使用 HiPerGator 自身的命令和文档。
