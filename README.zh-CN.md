# ICIC 资源看板

[English](README.md) | 中文

[打开实时看板](https://icic-robot.github.io/icic-resource-board/)

ICIC 资源看板公开、只读地展示 UF HiPerGator 上 `du.j` 组的共享配额、Slurm 队列以及 `/blue/du.j` 存储用量。组内成员可以用它查看当前需求、理解共享 QOS 余量，并判断下一个作业适合申请多少资源、何时提交。

本看板并非 UF 官方服务，也不能替代 Slurm 这一权威数据源。

## 只读边界

看板不能提交、取消、重新排队、调整优先级或修改任何 HiPerGator 作业，也不能更改账户、QOS 限额、分区、预约或资源配额。采集器只读取调度器信息，再生成字段范围受限的公开快照。

公开快照包含用户名、作业名称和 ID、资源请求、作业状态、调度时间窗口及每位成员的存储总量；不包含节点名、执行命令、工作目录、环境变量、凭据及未识别的 Slurm 字段。网页不会收集 UF 密码、SSH 密钥或登录会话。

## 运行方式

1. HiPerGator 的 Slurm `scrontab` 每 5 分钟触发一次 `duj-github-snapshot`。
2. 每次运行申请 1 个 CPU、512 MiB（0.5 GiB）内存，不申请 GPU，在 `hpg-dev` 中最长运行 2 分钟。
3. 采集器读取 `du.j` 的 Slurm 队列和 QOS、7 天 `sacct` 记录、各分区 `sinfo` 空闲情况以及 `/blue/du.j` 配额（共约 2–3 秒），生成公开的 `status.json` 快照（约 20 KB）。
4. 仅限本仓库的 GitHub Deploy Key 将快照推送到 `data` 分支。
5. GitHub Pages 从 `main` 分支发布看板。访问者的浏览器每 2 分钟检查一次快照，并缓存最近一次成功读取的数据。

发布任务本身是普通 Slurm 作业，因此会短暂出现在队列里。它不会常驻运行，也不会占用 GPU。

### 存储数据采集

Lustre 只允许每个用户查看自己的配额，因此成员存储用量有两种来源：

| 来源 | 方式 | 显示为 |
| --- | --- | --- |
| 组总量 | 每 5 分钟对 `/blue/du.j` 项目执行 `lfs quota -p` | 精确 |
| 成员自报（自愿） | 成员自己的 scrontab 每 3 小时运行 `report_storage.sh` 的私有副本（位于 `~/.local/bin`），将本人的 `lfs quota -u` 总量写入 `storage-reports/<uid>.json` | **精确** |
| 每日扫描（兜底） | `scan_storage.py` 每天 04:30 对每位成员的顶层目录运行 `du`（`hpg-default`，4 CPU，2 GiB，≤ 3 小时） | **扫描**；部分子目录组内不可读时为 **≥ 部分扫描**；整个目录不可读时为 **目录不可读** |

未能归属到成员的部分显示为 **未归属**（组总量 − 已统计成员），主要来自不可读目录。只公开总量和文件数，不公开路径。只有文件所有者与报告中的用户一致时，发布器才接受自报数据。

想分享自己的精确用量，在 HiPerGator 上运行一次（用 `--uninstall` 停止）：

```bash
/blue/du.j/jinjiaguo/duj-github-snapshot/report_storage.sh --install
```

采集器源码保存在 [`collector/`](collector/)，部署于 `/blue/du.j/jinjiaguo/duj-github-snapshot/`。

## 各板块含义

### 同步状态与数据来源

页头显示快照的生成时间，而不是打开网页的时间。**实时快照**表示当前读取的是 GitHub 实时数据，**浏览器缓存**表示正在显示浏览器之前保存的最后一份有效数据，**预览数据**表示演示内容而非真实队列。出现延迟或过期标记时，不应依赖这些数字安排作业，应等待数据恢复或直接查看 HiPerGator。

### 资源概览

- **CPU 核心、内存和 GPU** 表示组内运行中作业已获得的资源与共享 QOS 上限。每条进度条按成员分色（颜色与成员列表一致），斜纹部分为排队需求。
- **存储** 表示 `/blue/du.j` 用量与组配额，按成员和“未归属”拆分。
- 达到 85% 显示 **接近上限**，用满显示 **已满**。剩余数字表示 QOS 余量，并不承诺物理节点当前一定可用。

资源分配量不等于利用率。例如，一个作业即使没有充分使用四张 GPU，看板仍会显示它已分配四张 GPU。分析实际利用率时应查看作业日志和节点级工具。

### 成员

每位成员一行：运行/排队作业数、已分配的 CPU、内存、GPU，以及带来源标签的存储用量。点击表头可排序，点击成员可将任务列表筛选为该成员。

### 下一个预计启动任务

这里显示 Slurm 当前预计最早开始的排队作业，以及预计开始和结束时间。优先级、预约、依赖关系、作业实际时长和集群可用性都会改变估算结果，因此倒计时只用于规划，不代表资源已经得到保证。

### 排队请求

这里汇总组内排队作业申请的 CPU、内存和 GPU。这些数字表示正在等待的需求，并非已经占用的资源。排队需求越大，通常意味着竞争更明显、等待可能更久。

### QOS 配额

- **组 TRES** 是 Slurm 报告的 CPU、内存和 GPU 共享请求上限。
- **最长运行时限**是在该 QOS 下允许申请的最长 wall time。
- **每位用户可提交任务数**是 Slurm 报告的单用户提交上限。

分区策略、预约、账户关联和物理集群可用性还可能带来额外限制，因此仅有 QOS 余量不能保证新作业立即启动。

### 集群实时空闲

来自 `sinfo`：按分区统计 HiPerGator 全体用户共享的物理空闲 GPU（以及 `hpg-default` 的空闲 CPU 核心）。数据汇总后发布，不包含节点名。**单节点最多 N** 对多卡任务很关键：单节点 8 卡的任务无法使用分散在各节点、每节点 2 张的 14 张空闲卡。宕机、排空或维护中的节点不计入。

### 我的任务能启动吗？

输入 GPU 类型、数量、CPU、内存和时长后，规划器依次检查：QOS 上限与运行时限（超出则永远无法启动）；组内当前余量（如已满，估算运行中任务用满时限后何时释放足够资源）；组内已排队的需求；以及该分区是否有单个节点具备足够的空闲 GPU 或核心。输入会保存在浏览器中。结果仅供参考，实际顺序由 Slurm 优先级与回填调度决定。

### 任务

同一成员的相同请求（例如作业数组元素）会合并为一行并显示 `×N`，点击 **显示 ID** 可展开各个作业 ID。“时间”列显示运行中作业距结束、排队作业距预计开始还有多久。Slurm 原因代码会翻译为易读说明，悬停可查看原始代码。

- **运行中** 表示 Slurm 已经分配了请求的资源。
- **排队中** 表示作业仍在等待，应结合详情判断为什么没有启动。
- **已预约** 表示设定为稍后开始的任务（`--begin` 或 scrontab），不计入排队需求。
- 时间和原因都是快照信息，可能在下一次调度更新时改变。

### 最近 7 天

来自 `sacct`，包含已结束任务：每小时平均 GPU（或 CPU）使用量与 QOS 上限对比、按成员堆叠的每日 GPU/CPU·小时，以及每位成员的总量、已结束任务数和失败率（失败、超时、内存不足或节点故障 ÷ 已结束）。悬停可查看详情，可用 GPU/CPU 切换。

### 存储趋势

发布器在 HiPerGator 上每约 6 小时记录一个存储数据点，保留 90 天。积累约一天后，存储面板会显示最近一周的平均日增长量，以及预计多少天后用满配额。

### 链接与分享

筛选状态保存在网址中，例如 `?member=xianyao.li&filter=pending&lang=zh` 会打开相同视图。

## 如何据此安排作业

提交作业前：

1. 确认页头显示最近已同步、页脚标记为**实时快照**，且最近同步时间足够新。如果数据延迟，应直接查看 HiPerGator。
2. 将计划申请的 CPU、内存、GPU 和 wall time 与 QOS 配额比较。超过限制的请求需要先调整。
3. 同时查看当前分配量和排队需求。如果所需资源已接近共享上限或队列需求很高，应预期需要等待；时间敏感时可先与当前资源使用者协调。
4. 作业需要特定 GPU 型号时，应查看 GPU 类型，不能只看 GPU 总数。
5. “我的任务能启动吗？”与“下一个预计启动任务”只能用于粗略判断时间，最终调度决定由 Slurm 作出。
6. 查看“集群实时空闲”，确认单个节点能否容纳你需要的 GPU 数。

提交后，在**任务**中找到自己的作业。针对单个作业判断问题时，它的状态和原因比汇总数字更有用。需要权威结果或更详细的信息时，应使用 HiPerGator 自身的命令和文档。
