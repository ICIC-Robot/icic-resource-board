# ICIC 资源看板

[English](README.md) | 中文

[打开实时看板](https://icic-robot.github.io/icic-resource-board/)

ICIC 资源看板公开、只读地展示 UF HiPerGator 上 `du.j` 组的共享配额和 Slurm 队列。组内成员可以用它查看当前需求、理解共享 QOS 余量，并判断下一个作业适合申请多少资源、何时提交。

本看板并非 UF 官方服务，也不能替代 Slurm 这一权威数据源。

## 只读边界

看板不能提交、取消、重新排队、调整优先级或修改任何 HiPerGator 作业，也不能更改账户、QOS 限额、分区、预约或资源配额。采集器只读取调度器信息，再生成字段范围受限的公开快照。

公开快照包含用户名、作业名称和 ID、资源请求、作业状态及调度时间窗口；不包含节点名、执行命令、工作目录、环境变量、凭据及未识别的 Slurm 字段。网页不会收集 UF 密码、SSH 密钥或登录会话。

## 运行方式

1. HiPerGator 的 Slurm `scrontab` 每 5 分钟触发一次 `duj-github-snapshot`。
2. 每次运行申请 1 个 CPU、512 MiB（0.5 GiB）内存，不申请 GPU，在 `hpg-dev` 中最长运行 2 分钟。
3. 采集器读取 `du.j` 的 Slurm 队列和 QOS，生成公开的 `status.json` 快照。
4. 仅限本仓库的 GitHub Deploy Key 将快照推送到 `data` 分支。
5. GitHub Pages 从 `main` 分支发布看板。访问者的浏览器每 2 分钟检查一次快照，并缓存最近一次成功读取的数据。

发布任务本身是普通 Slurm 作业，因此会短暂出现在队列里。它不会常驻运行，也不会占用 GPU。

## 各板块含义

### 最近同步时间与数据来源

这里显示快照的生成时间，而不是打开网页的时间。**公开快照**表示当前读取的是 GitHub 实时数据，**浏览器缓存**表示正在显示浏览器之前保存的最后一份有效数据，**预览数据**表示演示内容而非真实队列。出现延迟或过期标记时，不应依赖这些数字安排作业，应等待数据恢复或直接查看 HiPerGator。

### 资源概览

- **CPU 核心、内存和 GPU** 表示组内运行中作业已获得的资源，以及 Slurm 报告的共享 QOS 上限。
- 剩余数字表示 QOS 余量，并不承诺物理节点当前一定可用。
- 如果 Slurm 报告了设备型号，GPU 项会同时显示已分配或已请求的 GPU 类型。
- **活跃任务**统计运行中和排队中的作业；作业数组中的每个元素按一个独立作业计算。

资源分配量不等于利用率。例如，一个作业即使没有充分使用四张 GPU，看板仍会显示它已分配四张 GPU。分析实际利用率时应查看作业日志和节点级工具。

### 下一个预计启动任务

这里显示 Slurm 当前预计最早开始的排队作业，以及预计开始和结束时间。优先级、预约、依赖关系、作业实际时长和集群可用性都会改变估算结果，因此倒计时只用于规划，不代表资源已经得到保证。

### 排队请求

这里汇总组内排队作业申请的 CPU、内存和 GPU。这些数字表示正在等待的需求，并非已经占用的资源。排队需求越大，通常意味着竞争更明显、等待可能更久。

### QOS 配额

- **组 TRES** 是 Slurm 报告的 CPU、内存和 GPU 共享请求上限。
- **最长运行时限**是在该 QOS 下允许申请的最长 wall time。
- **每位用户可提交任务数**是 Slurm 报告的单用户提交上限。

分区策略、预约、账户关联和物理集群可用性还可能带来额外限制，因此仅有 QOS 余量不能保证新作业立即启动。

### 实时队列

每一行显示作业所有者、状态、请求资源、开始和预计结束时间，以及 Slurm 当前给出的原因。可以按用户名、作业名称或 ID 搜索，也可以只查看运行中或排队中的作业。

- **RUNNING（运行中）**表示 Slurm 已经分配了请求的资源。
- **PENDING（排队中）**表示作业仍在等待，应结合原因字段判断为什么没有启动。
- 时间和原因都是快照信息，可能在下一次调度更新时改变。

### 按成员统计

这里按成员汇总当前运行中和排队中的作业，以及已经分配的 CPU、内存和 GPU。它适合用来协调资源、判断应该联系谁，但不能衡量程序效率或设备实际利用率。

## 如何据此安排作业

提交作业前：

1. 确认数据来源为**公开快照**，且最近同步时间足够新。如果数据延迟，应直接查看 HiPerGator。
2. 将计划申请的 CPU、内存、GPU 和 wall time 与 QOS 配额比较。超过限制的请求需要先调整。
3. 同时查看当前分配量和排队需求。如果所需资源已接近共享上限或队列需求很高，应预期需要等待；时间敏感时可先与当前资源使用者协调。
4. 作业需要特定 GPU 型号时，应查看 GPU 类型，不能只看 GPU 总数。
5. “下一个预计启动任务”只能用于粗略判断时间，最终调度决定由 Slurm 作出。

提交后，在**实时队列**中找到自己的作业。针对单个作业判断问题时，它的状态和原因比汇总数字更有用。需要权威结果或更详细的信息时，应使用 HiPerGator 自身的命令和文档。
